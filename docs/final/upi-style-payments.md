# UPI-style payments: FacePay IDs, send, request, QR, activity, roles

FacePay is an **academic prototype with simulated money**. Nothing here is a UPI ID, a bank transfer or a real
payment rail. The balance, transfers and requests exist only in this application's database. The "@facepay" suffix
is only the app's own naming style.

## What changed

| Area | Behaviour |
|---|---|
| Roles | `customer`, `merchant`, `admin`. The customer app has no PCA/LDA/metrics/biometric diagnostics. The merchant dashboard sees its own payments and an aggregate security summary. The ML Lab is `/admin` only. The role is read from the database on every admin call; nobody can grant admin through the API (see "Creating an administrator"). |
| FacePay ID | Server-generated (`name.suffix@facepay`), normalized to lower case, unique, change-limited by a cooldown. Old IDs are kept in `facepay_id_history` so one cannot be re-claimed by someone else. Email is never shown to other customers. |
| Wallet | `users.balance` is a `NUMERIC(12,2)` cache of the ledger. Every movement writes a debit and a credit `ledger_entries` row in the same transaction, with row locks taken in a fixed order. No floats, no negative balances, an `Idempotency-Key` header makes retries safe. `python -m app.cli reconcile-ledger` recomputes balances from entries. |
| Send | Resolve recipient (name and masked ID only) -> amount -> note -> review -> face verification with basic liveness -> explicit confirmation -> single-use authorization -> transaction -> receipt. The backend re-validates recipient, amount, limits and balance before the face scan and again at confirmation. |
| Request | A request never debits anyone. The payer authorizes separately through the same face flow. States: Pending, Paid, Declined, Cancelled, Expired, with transitions enforced by the backend (a request that expires mid-payment cannot be paid). |
| QR | My QR encodes only the FacePay ID (or a merchant payment link). Scanning decodes in the browser (jsQR), the value is validated, and the **server** resolves it. Anything else (a web address, text) is refused. Manual ID entry is the fallback. |
| Activity | One customer feed with All, Sent, Received, Successful, Failed, Pending filters, search, pagination and a detail page. A customer only ever receives their own rows. |
| Authorization | The single-use ticket is bound to payer, recipient or merchant, amount, currency, reference, session, model version and expiry (120 s). SHA-256 hashed at rest. Step-up PIN is structured in for large amounts and repeated failures. |
| Face-auth UX | Failures are classified: mismatch, camera error, poor quality, liveness, no enrollment, model unavailable or version mismatch, network error and server error. A server fault is never reported as "face did not match". Thresholds were **not** changed to improve success rates. |
| ML Lab (admin) | PCA explained and cumulative variance, LDA class separation, classifier comparison, confusion matrices, genuine rejection and impostor acceptance rates, dataset and methodology, model version and training status, and live outcome counts. Offline benchmark numbers come from `app/ml/reference/orl_final_evaluation.json` (the public AT&T/ORL set, generated by the repo's evaluation script) and are labelled as such. Live counts come from `authentication_logs` and are labelled as outcomes, not error rates. |

## New and changed API routes

Customer (JWT, role `customer`): `GET /wallet`, `GET|PUT /facepay/me`, `GET /facepay/resolve`,
`POST /facepay/qr/resolve`, `GET /facepay/contacts`, `POST /transfers`, `POST /transfers/{id}/cancel`,
`POST|GET /requests`, `GET /requests/{id}`, `POST /requests/{id}/pay|decline|cancel`,
`GET /activity`, `GET /activity/counts`, `GET /activity/{ref}`.
Merchant: `GET /merchant/security-summary`. Admin: `GET /admin/ml/overview|analysis|benchmark|outcomes`.
Existing payment, face and auth routes are reused (the transfer checkout uses the same `/payments/...` face flow).
Responses never contain embeddings, vectors, keys, raw thresholds or other customers' data. CORS now also allows the
`Idempotency-Key` request header (found by the browser suite; a plain API test client does not do a preflight).

## Database

Migration `0007_upi_style_payments` (backward compatible, upgrade/downgrade/upgrade tested on seeded data): adds
`users.facepay_id`, `facepay_id_changed_at`, `balance`, `facepay_id_history`, `ledger_entries`, `payment_requests`,
new nullable columns on `payment_sessions` (kind `TRANSFER`, payee, request link, idempotency key) and
`transactions` (kind, recipient). The `admin` role value already existed in the schema. Existing customers get a generated FacePay ID, and a ledger entry for the
opening balance. Existing rows are not deleted or rewritten, and historical simulated merchant payments are **not**
subtracted from that opening balance.

## Creating an administrator

There is deliberately no endpoint that grants a role. On the Render service Shell (or locally):

```bash
cd backend
python -m app.cli create-admin someone@example.com     # the account must already exist
python -m app.cli remove-admin someone@example.com
python -m app.cli reconcile-ledger                      # prints any balance that disagrees with its ledger
```

The account signs in again to receive a token with the new role. Demotion or disabling takes effect on the very next
request because the database role is checked on every admin call.

## What is still not claimed

* No protection against printed photos, replayed video, masks or deepfakes; the liveness check is basic.
* The in-memory rate limiter is per process (one Render instance).
* Simulated camera only was used for automated browser tests; a person on a real webcam was not.
* Production (Render, Vercel) was not touched or tested by the build session.
